## 1. 来源、范围和交接

课程任务书要求 M3 包含故障上报、派单、维修中状态、超时升级、完工验收与评价，并通过跨模块链路影响座位可预约性。本文件细化本人负责的前三组需求；维修、超时、验收与评价由另一位成员继续补充，不能因未在本轮实现而从模块范围中消失。

依据：[模块边界](../architecture/module-boundaries.md)、[D 实现契约](../../contracts/platform-api.md)、[跨模块契约草案](../../contracts/README.md)、[需求登记](../../spec/requirements.json)。

首轮交接结果：创建得到待派单工单；管理员派单后得到已派单工单，供同学实现后续维修。建议状态名 PENDING_DISPATCH / ASSIGNED，需双方确认。首轮上报和派单不触发 M1 下架；维修开始/验收恢复关联既有 CF-INT-002/003，由后续维修流程实现。

编号分配：CF-M3-001 上报，CF-M3-002 查询，CF-M3-003 派单。后续编号按本登记续编；仓库外此前分工建议的编号仅为草案，不作为实现依据。

## 3. CF-M3-001 故障上报

输入建议：roomId、faultType、description、幂等键；操作者、初始状态、所属院系和创建时间由服务端确定。禁止客户端指定 reporterId、dispatcherId、status 等受控字段。

| 验收编号 | 场景与可观察结果 |
| --- | --- |
| R01-AC01 | 已登录且授权用户提交有效 ROOM、合法类型和描述，产生一张持久化工单，唯一 ID/展示编号、真实 reporterId、房间/院系来源、服务端时间和待派单状态可查询；维修人员为空 |
| R01-AC02 | 未登录/失效会话或无报修资格提交被拒绝，无工单、历史或业务待发送事件新增 |
| R01-AC03 | 不存在、非 ROOM、effectiveActive=false（包括父级停用）的资源被拒绝，不落业务数据；D 不可用时不绕过校验 |
| R01-AC04 | 未知类型、纯空白、少于 5 或多于 1000 码点描述、伪造受控字段均拒绝；5/1000 边界通过，4/1001 失败（长度方案待确认） |
| R01-AC05 | 同一用户同键同内容重试（含响应丢失后）返回同一工单；同键不同内容冲突；并发重试不生成多张工单 |
| R01-AC06 | 创建工单、创建历史与必要 outbox 事件在同一事务提交；故意触发事务失败时均不部分落库 |

## 4. CF-M3-002 工单查询

提供本人分页列表与详情、授权范围内的管理列表与详情。建议按创建时间倒序并以 ID 稳定排序，分页复用 D 的 items/page/size/total 格式；按状态/房间筛选仍须先限制可见范围。

| 验收编号 | 场景与可观察结果 |
| --- | --- |
| R02-AC01 | 报修人仅查询本人记录，列表和详情展示编号、房间、类型、描述、状态、创建时间、派单结果及可见状态历史 |
| R02-AC02 | 猜测他人工单 ID、修改筛选条件或分页参数，不能得到他人受限数据；建议详情统一返回 404 避免泄露存在性 |
| R02-AC03 | 管理员仅看到授权院系/资源范围；具有明确全局业务权限者才可跨范围；列表 total 也不包含不可见记录 |
| R02-AC04 | 未登录、过期/停用账号查询被拒绝；权限撤销后下一次请求按 D 实时授权结果处理，不仅依赖前端菜单 |
| R02-AC05 | 空列表返回正常空态；非法分页拒绝；查询不暴露密码、令牌、服务密钥或未授权的用户资料；历史房间停用不导致历史工单消失 |

已指派维修人员对本人任务的查询权限由同学补充；不能因此提前开放全量工单。取消、验收及评价字段按后续契约扩展。

## 5. CF-M3-003 管理员派单

输入建议：工单 ID、assigneeId、expectedVersion、幂等键。初次派单仅允许待派单状态；成功后转已派单。客户端不能决定管理员身份、时间或院系。

| 验收编号 | 场景与可观察结果 |
| --- | --- |
| R03-AC01 | 具备派单权限且覆盖工单范围的管理员，为有效合资格维修人员派单；状态、人员、派单人、时间、版本及状态历史一起持久化 |
| R03-AC02 | 普通报修人、无派单权限管理员、跨授权范围管理员操作被拒绝，原工单不变 |
| R03-AC03 | 不存在、停用、无维修资格或不覆盖工单范围的人员不能被指派；不能仅依赖前端下拉选项校验 |
| R03-AC04 | 同一操作键同内容重试返回原结果，不重复增加历史或通知；同键不同人员/内容返回冲突；业务版本变化后旧重放不得再次覆盖当前状态 |
| R03-AC05 | 两名管理员从同一工单版本同时给不同人员派单，仅一个转换成功，另一个冲突；数据库、历史和 outbox 中只有一份成功派单事实 |
| R03-AC06 | 已派单/维修中等非法阶段的新派单请求被拒绝，不通过接口隐式改派；旧 expectedVersion 被拒绝 |
| R03-AC07 | 派单事务写入稳定 eventId 的通知/审计待发送事件；D 不可用不撤销已成功派单，重试不重复投递；展示已派单不等于通知已送达 |

## 6. 数据、接口与安全边界

- M3 自有数据建议含：工单 ID/展示编号、roomId、房间所属院系和当时资源版本、reporterId、类型/描述、状态、assigneeId、dispatcherId、创建/派单时间、并发版本；另有历史、幂等记录和 outbox。具体表结构先评审，再写版本化迁移。
- 身份从 HttpOnly CF_SESSION 的服务端校验得到；内部调用使用 M3 独立服务凭据。浏览器写操作有 CSRF 防护；D 不可用时受保护写入拒绝。不得自建与 D 冲突的账号系统。
- D 当前 authorization 面向会话权限校验，不是“验证任意 assigneeId 资格”的现成接口，需补齐契约；不得直接查 D 表或擅自开放 users.manage。
- 时间以 UTC ISO-8601 存储/传输，Asia/Shanghai 展示；错误与请求追踪格式沿用项目契约。具体 API 路径尚未冻结，需与共享前端代理协调，不能让 M3 请求被现有 /api 代理全部转到 D。
- 仅通过 D 读取主数据、发送通知和归集审计；M1 负责可预约性。不得用上报/派单去直接修改座位表。
- 描述按纯文本呈现，避免 HTML 执行；审计不包含完整敏感描述、密码、Cookie 或服务凭据。留存期限及敏感内容处置待评审。
