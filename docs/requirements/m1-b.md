# M1-B 签到、提醒、违约与运营实现范围

日期：2026-10-31。关联需求：CF-M1-007～011。状态：代码与本地隔离验证入口已完成，签到、模拟提醒、违约历史和运营看板已由用户人工确认；尚未代表D负责人评审、远程CI、部署或完整跨模块联调完成。

本文是M1-B协作开发的稳定入口，说明职责、核心实现和跨模块边界。阶段演进与历史决策见[接入说明书](../handoffs/m1-b.md)，具体HTTP字段以`contracts/`中的接口契约为准，测试操作不在本文重复展开。

## 职责与边界

- M1-B负责每日教室签到码、本人签到、座位使用状态与退座、预约提醒、未签到违约终结，以及管理员预约运营查询。
- M1-A负责座位查询、个人预约创建、本人历史/再次预约和统一占用协调。A/B共用M1的五状态模型、预约表、版本、转换事实和事务锁，不建立两套预约实体或绕过统一状态入口。
- D负责身份、角色权限、院系与空间主数据、站内信、邮件任务和审计基础设施。M1-B只调用D公开契约，不读取或修改D业务表，不根据角色名称自行推断权限。
- M2负责整教室申请审批，M3负责维修工单。M1-B不实现审批或工单业务，也不自行删除外部占用来源；维修导致的系统终止使用`DISRUPTED`语义并免记学生违约，实际触发契约仍待相应负责人评审。
- 当前代码只完成本地应用和隔离验证，不包含华为云部署、真实SMTP服务商验收、全组发布或生产规模承诺。

## 共享状态与一致性规则

| 状态 | M1-B含义 | 是否继续阻止个人冲突预约 |
| --- | --- | --- |
| `CONFIRMED` | 已预约、等待签到 | 是 |
| `CHECKED_IN` | 已签到、正在使用 | 是，直至原预约结束或完成 |
| `COMPLETED` | 正常退座或到时完成 | 否 |
| `NO_SHOW` | 超过截止点仍未签到，已记录违约 | 否 |
| `DISRUPTED` | 因维修等系统原因终止，免违约 | 否，但不解除对应外部限制 |

所有影响预约有效性的转换复用M1-A确定的用户锁、教室锁和固定加锁顺序，在锁内重读预约、服务端时间和在线权限，并通过当前状态与版本条件更新。状态、版本、转换、违约和业务outbox中属于同一动作的事实在一个事务内提交；失败整体回滚。重复请求、并发扫描和进程重启不能重复签到、重复违约或重复创建同类业务事实。

预约时间和事件使用UTC绝对时间保存，业务日与页面按`Asia/Shanghai`解释。客户端时间、请求体中的用户编号或前端页面状态都不是权威依据。

## 核心实现逻辑

### 签到与座位使用

教室签到码由独立密钥、稳定教室编号、用途版本和上海自然日通过HMAC派生，每日轮换且不落库。空间管理员只能查看其有权管理且属于本院系的教室码；学生只能对本人`CONFIRMED`预约提交6位码。

签到窗口为`[startAt - 20分钟, startAt + 15分钟)`，边界与状态均以锁内服务端时间为准。窗口尚未开始时返回明确的“过早签到”冲突且不累计错误码失败次数；窗口内的正确码原子完成`CONFIRMED -> CHECKED_IN`并记录服务端签到时间。错误码可重输，但由数据库保存跨实例失败次数和封锁时间。正确签到后进入使用状态，计时以服务端保存时间为准；主动退座或预约结束把`CHECKED_IN`原子转为`COMPLETED`，终结记录不能被旧请求复活。

### 预约提醒

后台按服务端时间为仍为`CONFIRMED`的预约生成两类唯一事实：开始前15分钟提醒，以及开始后10分钟仍未签到提醒。M1在自身outbox中保存业务事实，通过D公开资源接口补全教室、座位和上海时间，再分别投递站内信与邮件任务。

扫描和认领使用数据库租约及`SKIP LOCKED`，失败后指数退避。业务事实和D接收均使用稳定事件编号去重；SMTP不确定响应只能保证至少一次发送尝试，不能承诺绝不重复。前端弹窗通过轮询提示新站内信，最终记录与已读状态仍以D通知中心为准。

### 违约、释放与历史

生命周期任务扫描已到`startAt + 15分钟`且仍为`CONFIRMED`的预约，权威转换仍在统一锁事务中完成。一次事务同时写入`NO_SHOW`状态与版本、转换记录、一次违约和唯一通知事实。`NO_SHOW`退出个人有效占用集合，原座位可供后续个人预约，但不会删除M2/M3等其他来源限制。

签到与超时竞争由服务端时间、锁内状态和版本共同决定：合法窗口内签到先成功则不违约；到达或超过截止点时先确立`NO_SHOW`并拒绝迟到签到。本人历史保留签到、完成、服务端使用时长和违约原因，以文字、图标和颜色共同区分状态；列表由服务端按单一状态和预约开始日期筛选，上海自然日的结束日期按包含当天处理，游标与当前用户及筛选条件绑定，不能跨条件复用。

### 预约运营

运营查询使用独立权限`seats.operations.read`，该权限只登记到D目录，不自动授予`ADMIN`、`MEMBER`、`SEAT_USER`或已有用户。每次查询通过D在线会话取得身份和院系，只能读取本院系教室及座位范围；越范围筛选返回403，D不可用时失败关闭。

接口使用只读事务，支持最长31天以及教室、座位、状态筛选和不透明游标，返回预约明细、五状态分布、签到率、违约数、预约时长、实际使用时长、预约时段实际利用率和资源排行。M1不选择或返回预约人的姓名、账号、用户编号、邮箱等身份信息。当前统计只覆盖M1个人预约，不把尚未接入的M2整室占用、M3维修或物理容量解释为完整校园利用率。

## 数据与公开契约

M1拥有自己的`m1` schema并只通过版本化迁移演进：

- V1：预约、创建幂等记录和业务outbox；
- V2：签到转换与失败限流；
- V3：提醒任务的重试、租约和投递状态；
- V4：违约记录与生命周期扫描索引；
- V5：预约运营时间、教室和座位查询索引。

D的邮件任务由D V4维护，运营权限目录由D V5维护；M1不得在自己的迁移中修改D表。主要公开契约为[签到与使用状态](../../contracts/m1-check-in-api.md)、[本人历史与筛选](../../contracts/m1-history-api.md)、[预约提醒](../../contracts/m1-reminder-api.md)、[预约运营](../../contracts/m1-operations-api.md)和[D公共接口](../../contracts/platform-api.md)。契约变化涉及其他模块时，必须由受影响负责人评审，不能只同步修改调用方代码。

## 安全与数据最小化

- 用户身份来自已验证的D会话；M1再次执行具体动作权限、本人记录或院系资源范围检查。
- 浏览器写操作使用精确Origin、Fetch Metadata和会话绑定CSRF；内部调用使用独立服务凭据。
- 签到密钥、CSRF密钥、服务密钥和SMTP凭据只通过环境变量或密钥服务注入，不写入仓库、日志或业务响应。
- D、M1数据库或权限服务不可用时，受保护操作失败关闭，不使用无范围缓存继续放行。
- 运营统计遵守数据最小化，不提供学生身份、行为画像或跨院系明细导出。

## 协作接入规则

- M1-A修改预约状态、表结构、有效占用集合或锁顺序时，必须同时评估签到、超时、自动完成和运营统计；M1-B不得绕过A/B共享入口直接更新状态。
- D修改身份、资源、通知或权限返回时，应保持公开契约兼容并通知M1；新增运营权限不代表已有管理员自动获得业务读取资格。
- M2/M3接入时只通过评审后的来源契约影响M1可用性或`DISRUPTED`转换，不共享ORM实体，不直接写M1预约表，也不把系统中断记为学生违约。
- 各服务维护自己的迁移、测试数据和回退策略。数据库迁移与应用回退分开考虑，不假设回退二进制会自动撤销schema。
