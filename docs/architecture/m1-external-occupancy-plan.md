## 先理解三个业务例子

| 情况 | M1应承担的行为 | 其他方责任 |
| --- | --- | --- |
| A101的09～10点已有个人预约，M2申请同段整室占用 | 在同一事务保护下拒绝M2冲突占用，保留原个人记录；不泄露学生身份 | M2决定申请显示资源冲突、后续调整或撤销 |
| A101同时有维修工单甲、乙，只解除甲 | 乙仍限制全室；两者均解除后仍须检查M2占用、D启停/开放等 | M3决定每个工单何时合法解除 |
| 某来源的释放版本已处理，迟到的旧“启用”重试到达 | 返回旧请求/当前来源结果，不重新占用 | 调用方用原来源/版本查询恢复，不把超时当失败 |

候选计算建议：D有效且开放、没有相交M2占用、没有生效维修限制，再排除个人座位占用和本人时段冲突。查询仅给候选；个人提交须在共同事务锁内重读外部来源，防止查询后来源改变。恢复D停用或解除一个来源，都不能清除其他来源。

## 模型候选与取舍

推荐在M1自有schema新增版本化迁移（拟V2，评审后才编写），维护来源状态与操作结果；不改原V1、D/M2/M3表或共享ORM实体。相比每座位复制一个停用标记，按来源记账更容易独立解除和追溯，避免恢复一间教室时覆盖其他工单。

拟来源唯一键为`(sourceType,sourceId)`，sourceType由认证服务/路由确定，不能信任请求体自报。每个来源固定关联原教室；迁移教室/更改已批准时段建议另建来源或先释放重提，规则须M2/M3共同确认。个人来源仍由reservationId标识，不把旧个人预约复制进另一个可独立更新的占用表。

拟来源记录保留roomId、生效区间、当前有效状态、有效版本和已处理最大操作版本；操作记录保留版本、规范化意图摘要、接受/业务冲突结果。有效状态与已处理结果需区分：失败操作不能误清除旧占用。释放保留记录/版本屏障，不能硬删除后接受旧消息；未见过启用的先到释放也应保存屏障。

同来源同版本同意图重放结果；同版本不同意图409；旧版本不覆盖新状态。建议请求发送完整目标状态以支持版本跳跃，拒绝是否推进操作屏障、重放返回原操作结果与当前来源状态的具体字段须评审。释放后用更高版本重新启用同一来源、M3重新打开工单，尚未决定，不能把防旧消息复活偷换成任意重新启用都获批。

M2时段粒度/最长时长由M2决定，不能自动套用个人整点/四小时/提前一天规则。维修可能即时开始且持续到验收，可讨论开放结束时刻的限制；不擅自给维修自动过期时间或自动恢复。时间都以绝对时刻保存，边界采用[startAt,endAt)。

## 原子性、认证与网络恢复建议

1. 所有影响可用性的写操作共享当前教室事务锁命名空间。M2/M3来源写入必须与个人创建互斥；同来源操作还须序列化。SQL冲突检查、来源状态、操作结果和必要待发事件在M1同一事务保存，不先查空闲后无锁写入。
2. 冲突业务结果如需幂等保存，先提交操作结果再生成409响应；不可通过抛出异常把记录回滚后声称重复请求结果已经保存。鉴权/格式拒绝不写占用或操作记录；DB/网络错误不记录虚假的业务成功。
3. 读可用性使用一个一致的M1读取快照整合各来源；D仍通过原公开接口读取。D停用与M1提交间的跨服务竞态不会因加一张表自动解决，正式补偿策略单列未决。
4. 建议分别验证M2/M3服务凭据、按路由赋予最小动作权限；错误凭据401、已认证服务调用他方来源403，不接受浏览器CF_SESSION冒充服务。沿用D已有资源接口，不扩大本轮D三项补充授权、不把D的服务凭据验证当作M1已经验证调用方。
5. PUT只更新本服务来源；GET恢复也必须同服务鉴权且不泄露学生或另一模块细节。响应含sourceId、roomId、请求操作版本/结果、当前有效状态/版本。超时或503表示结果可能未知，原版本原意图重试/查询；查询404可能仍有在途请求，不证明原写入失败。

沿用仓库草案的拟路由：

| 动作 | 拟接口（待评审） |
| --- | --- |
| M2设置/释放、恢复当前来源 | PUT/GET `/internal/v1/room-occupancies/{applicationId}` |
| M3设置/解除、恢复当前来源 | PUT/GET `/internal/v1/maintenance-blocks/{workOrderId}` |
| 恢复特定操作结果 | GET上述来源路径附`operationVersion`，字段/缺失语义待确认 |

M2有效个人冲突、已有M2时段冲突和维修限制应明确返回409原因，不返回他人预约ID或姓名；参数400、资源缺失404、D/DB不可用503。预检查不构成占用承诺。重试必须同一来源和版本，不能通过换来源绕过业务重复申请规则（重复申请由M2负责）。

## 不能代为决定的边界

- M3遇到已有个人或M2预约：任务书要求维修下架和学生免违约，但立即终止哪些预约、未来预约如何处理、何时通知M2/B、恢复后能否复活旧记录，尚未决定。不能以保留个人预约阻止安全维修，也不能套用M2冲突拒绝规则。建议维修限制先成为独立事实，受影响预约处置再按共同批准规则原子落地；只阻止新预约而不解决既有预约/免违约，不能称M3完整联调完成。
- 用户于2026-10-29明确同意将以下原则作为M3评审建议：已确定受维修影响而必须终止的有效个人预约保留为历史、转DISRUPTED，不记学生违约；解除维修不自动复活已终止预约。这里不提前确定“受影响”的时间范围、立即终止/通知时点或B实现；M3及跨模块接口评审仍待，不能把A的同意记为M3本人已批准。待办见[评审清单](../process/m1-external-occupancy-review.md)。
- 维修若修改多名学生预约，不能先持有教室锁再逐个追加用户锁，违反现有全序会死锁。须设计并评审统一获取必要锁、锁内重读与集合变化时重试的流程，及B签到/超时并发的合法结果。本轮不提前写一个绕过B协议的通用取消方法。
- M2审批状态、释放未确认的页面、M3工单合法转换、运营通知和违约处理仍归对应模块；A实现接收和来源事实，不接管业务流程。
- 首次服务凭据配置/轮换、调用方资源权限范围、来源版本持久化、冲突操作的版本推进、重新启用策略、新迁移字段需组内评审。新schema仅写M1不等于免评审。
