# ADR-0003：M1 按用户与教室协调并发占用

日期：2026-10-28。状态：M1-A用户选择方案B，并决定M1内部共享设计；五种状态已确认，B交接延后至A完成。个人预约存储与事务锁已用真实PG验证，见 [存储方案](m1-storage.md) 与 [验证记录](../process/m1-storage-validation.md)。D/M2/M3相关schema和跨模块契约仍待评审，其写入/集成及性能测试尚未完成。

## 问题与候选

需同时防止同座位重叠预约、同用户跨座位/跨教室重叠预约，以及 M2 整室占用、M3 维修和个人预约相互覆盖。查询空闲不构成占用承诺。

| 候选 | 收益 | 代价 |
| --- | --- | --- |
| A：一个全局事务锁保护所有占用写入 | 协议简单、易审查 | 不相干教室也串行等待 |
| B：按用户和教室取得事务锁 | 同用户跨教室受保护，同室不同来源互斥；无关用户/教室可并行 | 必须统一锁顺序、状态读取时机和全部写入口 |

用户选择 B。AI 推荐依据是既覆盖本人跨教室冲突，也覆盖整室与单座竞争，并减少不相关写入间的等待；用户尚未提供自己的权衡表述。采用 PostgreSQL 事务级 advisory lock 的具体实现为方案建议；不额外引入 Redis。选型不意味着协作协议已被其他负责人接受。

## 设计约束

- 个人预约涉及用户和教室；M2/M3 写入至少涉及目标教室。同一 M1 数据库内统一协调，不跨模块写业务表。
- 所需锁按固定全序一次取得，采用稳定的类型命名空间及 UUID 映射；多服务进程使用同一协议。
- 取得锁后在 READ COMMITTED 事务内重新查询冲突和目标状态，不能复用锁前空闲结论。锁只覆盖短暂校验/写入过程，不覆盖整个自习时段。
- 取消、签到、超时、来源释放等有效性变更同样遵守锁协议；先读出的所属用户和教室必须是不可变关联，锁后再次读取状态。
- M3 对已有预约的取消/免违约不得临时逆序获取用户锁；采用经评审的独立处理流程。
- 使用事务级锁，事务结束自动释放；连接池不使用会话级锁。设置等待上限并明确暂时失败结果，不能把锁超时当作成功。
- 同一个事务保存预约、幂等结果和待发送事件；失败无部分占用残留。身份校验在每次重试继续执行。
- 幂等按调用主体与操作隔离；相同键不同载荷拒绝，旧来源版本不能恢复已释放占用。
- advisory lock 依赖所有写入方协作，不能阻止绕过协议的直接写表；使用约束、统一业务入口和并发测试补充保障。
- D 查询与 M1 本地写入并非跨库原子操作；不以此 ADR 宣称解决管理员停用竞态。

## 必须验证的行为

1. 两个独立连接同时预约同座位重叠时段，最多一份成功。
2. 同用户同时预约不同教室的重叠时段，最多一份成功。
3. M2 与个人预约竞争，同一资源时段不能双重成功；已有个人预约优先保留。
4. 两个维修来源解除一个后仍受限；所有维修解除不能清除 M2 有效占用。
5. 签到与超时、释放与旧版本重试的竞争只产生合法状态。
6. 在隔离副本故意删除关键互斥/冲突逻辑，对应测试应失败；恢复后再通过并保存真实证据。

依据：[PostgreSQL 17 官方锁文档](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS)。其中个人预约互斥、幂等、锁等待和回滚已执行本地验证；M2/M3及签到竞态仍为计划。
