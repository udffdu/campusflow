## 1. 本次建议交付什么

在**独立临时数据的本地演示**中完成：学生查询候选 → 选择座位 → 核对教室/座位/上海时段 → 点击“提交演示预约” → 成功后查看本人的该条记录。随后同一时段再次查询，体现本人时段互斥和他人占用。页面持续说明“仅本地演示，尚未校验整教室申请和维修限制”，不向学生承诺完整可预约。

| 路径 | 范围与取舍 |
| --- | --- |
| 先完成隔离个人预约演示（推荐） | 接通D鉴权/主数据、M1写入、重复请求恢复及本人单条读取；正式启动仍关闭写入口；本次无需改D公开契约或M2/M3接口 |
| 先完成统一占用再开放正式预约 | 需先具体设计并评审M2/M3来源协议、停用竞态与补偿，再交付完整可用性；范围更大，不能用本次个人预约批准代替对应评审 |

本轮不实现正式放行、全部历史列表/再次预约、主动取消、签到/提醒/违约或事件派发。本人**单条读取与按请求键恢复**只服务于本次提交闭环，不标记CF-M1-006全部完成。outbox仍是PENDING，不显示通知已发出。

既有`/seat-query`默认仍是只读，`canReserve=false`不变。建议独立演示页`/seat-reservation-demo`复用查询表单；只有隔离环境明确开放、且本人拥有相应权限时显示“提交演示预约”。新的GET能力描述区分`stage=PERSONAL_DEMO`、`canCreateDemoReservation`、`productionReady=false`，不将原canReserve翻成完整可预约承诺。

## 2. 开放范围与已有规则

- 生产应用缺省不注册/开放本轮创建POST和令牌入口，其他未支持方法继续405；不得只隐藏按钮而让接口可写。
- 演示开关只能由隔离测试/演示启动流程显式启用；建议加测试classpath启动标记和回环监听限制，缺少任一条件启动失败。数据库仍由该启动器创建独立临时PG，不连接现有5173/8080或正在使用的5174演示。正式jar不包含测试启动入口；配置开关不能被当作正式放行依据。
- 新阶段另用空闲端口（例如D18180、M118181、前端5274），冲突报错而不停止他人进程。用户自己在终端设置新演示密码，不在聊天提供。旧演示保留。
- 延续整点、本人有效时段互斥、五种状态、用户/教室有序事务锁、三表原子写入和精确插座查询；不重新询问这些已确认的决定。
- 窗口和时长仍强制配置。演示显式用PT24H/PT4H，**不把本次确认记作“一天等于滚动24小时”的正式业务确认**。正式解释、管理员配置方式、午夜表示仍待对应阶段。
- `requiresPower`继续是查询筛选；本次创建意图只包含指定座位与时段，不另加“必须有插座”的写入参数。确认页展示重新取得的属性；将来若增加属性承诺，必须一起纳入重复请求意图和校验，不能悄悄改变语义。

## 3. 拟议接口与身份

全部仍通过同源`/api/m1`代理；M1只读自己的表、用D现有HTTP契约核验身份和主数据，不共享D实体。

| 拟议接口 | 权限/行为 |
| --- | --- |
| GET `/api/m1/v1/reservation-capabilities` | 有效D会话；只描述本环境和当前用户能做的演示操作，不提升权限 |
| GET `/api/m1/v1/csrf` | 隔离模式＋`seats.reservations.create`；发M1自己的短期写入验证令牌 |
| POST `/api/m1/v1/reservations` | 隔离模式＋CSRF＋`seats.reservations.create`；body只有roomId、seatId、startAt、endAt，必需单个Idempotency-Key头 |
| GET `/api/m1/v1/reservations/{id}` | `seats.reservations.read.own`；只查本人该条，缺失和他人统一404 |
| GET `/api/m1/v1/reservation-requests/{key}` | `seats.reservations.read.own`；恢复本人已提交的请求，未见已提交记录404，不断言请求从未/不会成功 |

权限由服务端固定动作枚举指定，不能从前端permission参数获得。查询、创建、本人读取三项独立，只有查询权不能创建；创建权不隐含D目录权限，也不自动替代本人读取权。创建成功的响应可返回本次创建结果，但单独GET依然核验读取权限；GET403不能让前端把已经成功的POST误报为创建失败。

未知/重复字段、伪造userId/departmentId/source/status/resourceVersion等400。UUID及时间严格校验，UTC以Z结尾、按上海整点解释。资源版本只能由D返回并校验为正整数；目前适配器未映射version，实施时须补齐。第一笔创建201；相同请求重放200且`replayed=true`，返回原预约的当前状态；响应统一标记演示阶段、非正式可用性保证，不包含他人身份。

本人读取依据D身份＋预约归属，不因其后来换院系、教室停用或资源不存在而把既有记录当作新预约重新审核。当前D身份失效/无读取权限仍拒绝；D不可用503，不能拿旧会话缓存放行。名称补充不能让D资源目录故障掩盖已经存在的预约事实；本轮最少返回稳定ID、时段、状态和版本。

## 4. M1自己的写入保护，不修改D的安全策略

D的`/api/v1/auth/csrf`及CookieCsrfTokenRepository保护的是D接口；现有契约没有供M1调用的“验证D CSRF令牌”端点，不能只把D的令牌头转给M1就称为已验证。

建议M1使用**绑定当前CF_SESSION的短期签名令牌**，通过自己的GET入口取得，POST要求`X-M1-CSRF-Token`：随机nonce、过期时间、用途标记与会话绑定信息共同签名；令牌不包含原始CF_SESSION，签名密钥不出服务器。使用独立随机密钥，不能复用M1_SERVICE_KEY；在隔离进程环境注入，不保存到仓库。建议有效期15分钟，常量时间比较，格式/大小严格限额。无需新增CSRF数据库表；具体实现须测试篡改、跨会话、过期、密钥轮换及登录切换。

POST同时要求精确匹配受控配置的同源Origin；拒绝缺失、null、错误Origin和显式跨站Fetch-Metadata。不能把浏览器Host或未经信任的转发头当允许来源，不开启宽泛CORS；非浏览器集成测试也显式发送配置中的Origin。CSRF/Origin失败返回403专用码，不进预约事务；GET不创建预约。D登录/退出/改密继续用D原有CSRF逻辑。

令牌只能作写入保护，不能替代每次在线D鉴权。旧会话绑定的令牌不适用于新会话；成功提交不消费令牌，重复请求是否创建由幂等键决定。令牌过期可重新获取，重试仍保留原请求键；不对所有403或网络错误自动重发POST。正式部署的Origin、TLS和密钥管理仍需部署方案，不能把本地方案记为已部署。

## 5. 事务、重新校验与重复请求顺序

现有`ReservationStore.create`已经在REQUIRES_NEW/READ_COMMITTED中取得锁并优先检查旧请求，但尚未组合D/opening等创建校验。HTTP层先无锁查空位再调用create，或在外层包一个@Transactional，都不能代替其内部事务。

建议新增显式的应用层创建入口及存储事务扩展：

1. 验证演示开放、Origin/CSRF、严格载荷和请求键；在线D鉴权得到可信userId。身份不来自body。
2. 进入M1事务，按既有稳定全序锁住用户＋教室；锁超时和数据库故障安全失败，不修改三表。
3. 锁内再在线核验当前创建权限/身份，确认用户ID一致。D调用沿用同一个总预算，不因取锁、翻页或二次鉴权无限续期。无权限/失效时拒绝，即使旧请求已存在也不能匿名重放。
4. 查`(userId, key)`。旧记录且意图相同，直接返回**同一预约当前状态**；不再把它当新建去校验过去时段、已被自己占用或后来停用的教室。旧记录且意图不同，409，原记录/请求/事件均保持。
5. 仅全新请求在锁内调用受控校验回调，取得D当前ROOM和指定SEAT，验证类型/父子/院系关系、权限范围、effectiveActive、完整开放时段、可信资源版本；重新校验当前时间窗口/时长。D失败/字段异常503，实际资源停用或开放变化为明确409，不默认为可用。
6. D校验后再按当时的服务器时钟检查时间（网络等待不能让刚过开始时刻的预约成功），按READ_COMMITTED重新查个人占用；用户/座位冲突409。三表一次提交：CONFIRMED预约、请求去重记录、PENDING事件。

应用层不能先调用`queryForIdentity`来“验证新建”并误用其QUERY权限，也不能将同一次重放送进可用性查询后被自己的旧预约挡住。新的回调/存储组合须有真实数据库测试；保留原内部create以兼容已验证用例，但HTTP仅调用完整的本阶段应用入口。

幂等意图沿用用户、教室、座位、起止时间；D资源版本不是用户意图，版本变化不构成换请求。新需求不能直接把未来新的意图字段排除在摘要之外。现有三表足够本轮使用，预计不新增迁移；如实施发现确需schema变更，先更新具体方案，不修改V1来绕过演进。

**已知跨服务限制：**M1的数据库锁不能锁住D管理员的操作；即使锁内重新读取，D仍可在最后一次响应与M1提交之间停用资源。本次演示测试必须如实暴露这个边界，不承诺“重新读一次就完全消除竞态”，不擅自决定正式生效/补偿政策。M2/M3也没有因为个人预约锁正确而自动受到保护。这是正式入口继续关闭的原因之一。

## 6. 网络中断后的页面行为

一次明确的座位/时段选择生成一个随机请求键；重复点击、等待、网络超时、500/503重试始终保留同一个键和同一意图。换教室/座位/时段才是新意图，但旧请求结果未知时先提示核实，不让改表单抹掉待恢复请求。

同一标签页刷新可恢复pending意图/键（按当前用户隔离的sessionStorage，仅保存预约草稿，不存密码、CF_SESSION、服务密钥或CSRF令牌）。优先用本人请求查询恢复；查到则展示原记录，查不到可能仍在处理中，重试只能复用原键。退出/换账号清除草稿，不声称能在清理存储、换设备后凭空恢复丢失的键；完整历史列表为后续阶段。

没有读取权时仍可用同一键、同一意图重放POST取得本次结果；权限拒绝和未知结果分开显示。提交按钮等待中禁用只是交互保护，后端并发/幂等仍必须独立成立。成功后清理pending，保留返回记录；再查同段提示本人冲突。不能因为随后资源名读取失败、通知未派发或单条GET403而新发一个预约。

## 7. 失败语义与验收例子（拟实施，尚未执行）

| 场景 | 应有结果 |
| --- | --- |
| 学生甲乙都先查到S1，甲先提交成功 | 乙提交409座位冲突，不能都成功 |
| 同一学生同时订不同教室的重叠时段 | 最多一个成功；相邻且不重叠仍允许 |
| 相同用户/请求键/座位/时段重复提交 | 201后200，预约ID相同，三表只有对应一份记录/事件 |
| 首次已落库但响应中断，再用同键恢复 | 取到原记录；开始时间已过也不重建、不报“被自己占用” |
| 相同请求键改座位或时段 | 409幂等冲突，原记录不变 |
| D已停用资源，或已改为非本院系/非开放 | 新建拒绝；旧成功请求的重放不重新创建/误报新建失败 |
| 缺失/篡改/过期/跨会话令牌、跨站或错误Origin | 403且三表无变化；D的登录/退出保护保持 |
| 仅查询权、仅spaces.write、伪造用户/状态/版本 | 无权403或非法输入400，不能创建 |
| 本人读取别人ID/请求键 | 404，不暴露存在性；失效会话401，D连接凭据错503 |
| D超时、预算耗尽、DB/锁失败、提交响应未知 | 503/明确未知结果，页面保留原键；不自动换键创建 |
| 正式jar启动/缺省未开启、非回环演示地址 | 无创建入口或启动失败；直接HTTP也不能写，非只藏按钮 |

保留已通过的D24/M1123/前端22和真实网络28；实施有改变后运行适当回归并据实际结果登记新数量。新增真实D＋M1＋PG测试、独立连接并发、响应丢失后的恢复、三表逐行不变/事务回滚、CSRF与环境门禁、组件交互和真实浏览器。对关键门禁、幂等顺序、创建校验做隔离破坏实验，原始源码哈希不变。这里均是验收计划，不是新增测试已通过。
