# 模块边界与数据归属（讨论稿）

| 事实 | 唯一维护方 | 其他模块的访问方式 |
| --- | --- | --- |
| 用户、院系、角色、权限、数据范围 | D | 身份验证与授权契约 |
| 校区、楼栋、教室、座位、开放规则 | D | 主数据接口 |
| 个人预约、签到、违约、历史 | M1 | M1 API |
| 资源时段占用、维修限制及来源追溯 | M1 | M2/M3 的内部写入契约 |
| 教室申请、节点审批、超时与撤销 | M2 | M2 API |
| 工单、派单、维修、验收、评价 | M3 | M3 API |
| 投递记录、集中审计 | D | 通知与审计接收接口 |

可预约性是基础配置、身份范围、时间、个人预约、教室占用和维修限制的综合结果。
D 不维护一个可以覆盖上述事实的可预约布尔值。M1 不复制维护第二套空间主数据。
一次释放只改变指定来源，不清除其他占用或维修限制。

各模块各自维护业务授权、定时任务、待发送事件和状态恢复；D 不决定业务超时条件。
M2 的审批事实与 M1 的使用有效性分别展示：审批曾通过不代表之后没有维修影响。
资源被引用后优先停用，删除、开放时间变更和既有预约处置需明确生效规则。
