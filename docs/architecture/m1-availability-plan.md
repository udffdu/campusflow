# CF-M1-001：座位查询的下一步方案

日期：2026-10-28。状态：A 负责人已回复“我同意”，确认按推荐次序实现本步内部计算；AI 已完成内部代码和本地验证，用户随后报告80测试及构建独立复验通过。本文不是已评审的 D/M2/M3 契约。实际范围和结果见 [查询验证记录](../process/m1-availability-validation.md)。

## 1. 本步目标与边界

前一阶段已验证时间规则、个人预约落库、幂等及并发保护。本步准备让 M1 判断：给定教室、时段和经过授权的数据范围，哪些座位满足当前已接入的查询条件。

完整的“可预约”要求同时满足身份权限、院系范围、资源启用、整个时段开放、插座筛选、个人预约互斥、M2 整室占用及 M3 维修限制。不能把暂时未接入的条件当作默认满足。

推荐先实现 M1 内部的开放时间判断与个人预约占用查询；随后按评审后的契约接入 D、M2/M3 和页面。本步内部计算结果不能直接作为完整可预约 API 对浏览器开放，也不改变现有创建入口尚不具备完整业务校验的事实。

本步不需要数据库迁移。沿用 M1 自有预约表，主数据仍归 D，不复制 D 表或共享其 ORM 类。

## 2. 两种实施次序

| 次序 | 需要先准备什么 | 优点及代价 |
| --- | --- | --- |
| 一次性完成联调 | D 的权限、访问范围、插座词汇及 M2/M3 占用契约先评审 | 可以直接验收完整结果；当前依赖尚未确认，涉及的变更范围较大 |
| 分阶段接入（推荐） | A 先评估本方案；M1 内部计算使用明确的输入边界 | 先验证独立逻辑与真实数据库查询；完整 API 和页面验收仍要等待相关契约及集成 |

这只是实现次序选择，不重新选择已经确认的“用户＋教室事务锁”并发方案。

## 3. 已核对的 D 能力与待评审内容

证据来自当前仓库 [D API](../../contracts/platform-api.md)、`ResourceService`、`InternalController` 和 `Models`；没有查询或修改正在运行的演示数据。

| 内容 | 当前事实 | 本步处理与后续评审 |
| --- | --- | --- |
| 资源编号及层级 | 有教室/座位 ID、parentId、departmentId、version | M1 使用输入快照，校验座位确属指定教室，不自建主数据 |
| 有效性 | effectiveActive 包含父级停用影响；父级停用不一定改变座位版本 | 使用基础有效性输入；后续 D 适配层实时取值，不能只看座位版本 |
| 开放时间 | 教室每周 day=1～7、上海本地时间；空规则表示无已配置开放时段 | 必须覆盖完整预约区间；开放计算由 M1 执行 |
| 业务权限 | 当前目录只有 D 权限，没有 M1 预约权限 | D 负责人评审权限名称和角色映射；不把 spaces.read/write 当作预约授权 |
| 院系范围 | departmentId 表示资源归属，没有明确全校开放字段 | 归属不自动等于访问范围；内部计算只接收明确的授权结果，不从前端自报院系推导 |
| 插座 | features 是自由文本 | D 负责人评审统一标记及“座位有插座”的语义；本步不猜关键词，也不把教室有插座解释成所有座位都有 |
| 跨日开放 | 契约说跨夜拆分；实现使用 LocalTime 且要求 end>start，未明确 24:00 的表示 | 需 D 评审跨日/午夜边界表示；无法证明完整覆盖时不返回满足开放条件，不能擅自当作全天开放 |
| 主数据变化 | 查询资源和写入预约之间可能发生停用 | 重新查询仍不能提供跨服务原子性；生效边界和补偿须另行评审 |

上述待决问题不阻止独立的开放计算和个人占用读取测试；也不能通过虚构 D 已授权或返回空对象来跳过。

## 4. 拟实现的内部计算步骤

1. 复用 `ReservationPolicy` 检查整点、非过去、提前窗口与时长。继续注入参数和时钟，“1 天＝滚动 24 小时”仍保留为待确认的具体化建议。
2. 接收教室/座位的明确快照和已验证的授权范围；缺少必要授权信息时拒绝执行，不接受任意前端 userId 充当身份。校验资源类型、座位所属教室及基础有效性。
3. 将上海本地的每周开放规则映射到请求日期。整个请求区间都必须被开放区间覆盖；相邻开放区间可以连续覆盖，中间有空隙则失败。空规则不能解释为全天开放。
4. 从 M1 自有表读取请求时段内的有效个人预约：`CONFIRMED`、`CHECKED_IN` 阻止重叠；其余三种状态不阻止。区间采用 `[startAt,endAt)`，相邻时段不冲突。
5. 同时检查当前用户跨教室的个人预约冲突。如本人已经有重叠预约，返回明确的本人时段冲突结果，而不是继续推荐其他座位。
6. 输出经过上述条件筛选的座位 ID 及必要展示字段，不返回他人身份或预约详情。数据库失败应报告查询失败，不能伪装成“没有空座位”。

内部结果只覆盖明确执行过的条件。插座语义、M2/M3 条件和真实身份授权适配完成后，才能组合为完整业务查询。

查询不取得“占住座位”的锁，也不创建预约。查询结果随其他人提交而变化；最终提交继续在事务锁内重新校验占用，其他条件也须由未来完整应用层核查。不能凭此前看到空位就直接成功。

## 5. 本步验收例子（计划，尚未执行）

以下例子均假设预约时间参数合法，且没有额外未满足的条件；日期、身份与主数据使用虚构测试输入。

| 场景 | 预期行为 |
| --- | --- |
| 开放 09:00—12:00，请求 11:00—12:00 | 满足开放条件 |
| 开放 09:00—12:00，请求 11:00—13:00 | 不满足，结束前已有一小时不开放 |
| 开放 09:00—10:00、10:00—12:00，请求 09:00—12:00 | 满足，两个开放区间连续覆盖 |
| 开放 09:00—10:00、11:00—12:00，请求 09:00—12:00 | 不满足，中间存在空隙 |
| 没有开放规则，或上级资源停用 | 不列为满足条件的座位 |
| 座位在 09:00—10:00 有有效预约，请求 10:00—11:00 | 不因相邻预约而排除 |
| 座位在 09:00—11:00 有有效预约，请求 10:00—12:00 | 排除该座位 |
| 本人在其他教室有 09:00—11:00 有效预约，请求 10:00—12:00 | 返回本人时段冲突，不推荐换座 |
| 原记录为 NO_SHOW 或 DISRUPTED | 不再阻止个人预约；不据此推断维修等外部限制也已解除 |
| 座位来自其他教室、授权输入缺失、主数据格式无效 | 拒绝或明确报告输入不可用，不扩大范围 |
| 数据库访问失败 | 明确失败，与正常空结果区分 |

测试将直接执行开放计算与真实 PostgreSQL 读取，不 mock 掉被测逻辑；关键筛选通过隔离破坏实验确认能触发测试失败。保留现有 43 个测试，新增数量与结果只在实际运行后记录。

## 6. 用户与 AI 各自完成什么

- 用户现在学习：区分“查询时空闲”和“提交成功”；理解完整时段开放、相邻不冲突及本人跨座位互斥。
- 用户现在评估：是否按推荐的分阶段次序，先实现本方案中的 M1 内部计算。评估不是 D/M2/M3 已评审的替代证据。
- AI 在方案确认后完成：实现内部计算、只读存储查询、行为测试和破坏实验，维护需求映射及 B 说明书，提供人工复验命令。
- 用户在实现后验收：阅读具体结果，运行复验命令，再由 AI 按验收结果分步提交。
- D/M2/M3 的受影响负责人：在对应接口或其 schema 变更实现前评审具体契约。此时不要求提前联系 B；B 交接仍安排在 A 完成后。

本步遵守 [仓库协作规则](../../AGENTS.md)“先明确任务范围、依赖、验收标准和方案，再实现”，以及工作区要求用户理解并评估方案后实现。用户确认本步范围后已实现 M1 内部计算及只读查询；人工构建/测试复验以用户随后提供的80测试输出单独记录，不代表其他成员同意。资源类型通过内部 RoomSnapshot/SeatSnapshot 表达，真实 D 类型校验仍由未来适配层完成。
