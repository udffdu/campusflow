## 2. 直接沿用的既有约定

| 内容 | M1 接入方式 |
| --- | --- |
| 浏览器身份 | 沿用 CF_SESSION；M1 服务端提取 Cookie，不能让前端自报 userId 或读取 HttpOnly 会话 |
| 在线鉴权 | 调用 `POST /internal/v1/authorization`，请求沿用 `{sessionToken,permission,departmentId?}`；只把 allowed=true 作为相应权限检查通过，不能把 denied 响应中的 identity 当作放行证据 |
| 服务身份 | M1 服务端使用独立 M1_SERVICE_KEY；来源由 D 验证凭据，凭据不进入前端或 Git |
| 主数据 | 沿用 `GET /internal/v1/resources/{id}` 和带 type/parentId/page/size 的资源列表，不跨库读取 D 表 |
| 资源有效性 | 每次新业务获取基础有效性，检查教室、座位的类型/归属及 effectiveActive；不能仅凭 seat.version 没变沿用启用状态 |
| 时间 | UTC 绝对时间传输，上海本地时间计算每周开放；半开区间，空开放规则视为关闭 |
| 分页 | page 从0开始、size最多100；不能只取第一页便声称完整可用座位数。后续页失败须报告失败，不能冒充完整结果；跨页不承诺同一快照 |
| 占用 | D 不判空闲。M1 的查询不占座，创建时用既有用户/教室锁重新判断个人占用，后续加入其他来源 |
| 通知与审计 | 沿用现有内部接口及去重；M1保存自己的待发事件。当前D渠道为站内信，不能声称已实现邮件/微信 |

`authorization` 现有请求形状已经够用，下面的权限建议主要需要新增目录/角色映射，不必另造一套登录接口。

## 3. 三项原建议（随后获用户授权实现）

### 3.1 预约权限

建议登记三项职责明确的业务权限：

| 建议权限名 | 允许的动作 | 仍须执行的限制 |
| --- | --- | --- |
| `seats.availability.read` | 查询本人可预约候选座位 | 资源开放范围、基础有效性和完整可用性条件 |
| `seats.reservations.create` | 为本人创建预约 | 资源范围、时间、全部占用、幂等与并发检查 |
| `seats.reservations.read.own` | 查询本人历史/单条记录 | 查询条件强制使用已验证身份，不允许借管理员角色读取他人历史 |

命名依据：D的`Models.Authorization.permission`使用`[a-z.]{1,64}`校验，所以本稿采用seats前缀和点分段，避免提出带数字的m1前缀或带短横线的权限名而被现有接口直接拒绝。

建议新增普通预约角色 `SEAT_USER`，赋予上述权限；权限目录项建议global_only=false，才能由现有自定义角色接口授予。由 D 确定有预约资格的成员并在其现有角色集合上显式附加。现有 MEMBER 只表示可查看目录，直接给全部 MEMBER 预约资格会扩大权限；若 D 确认全部普通成员均有资格，也可以选择给 MEMBER 增权，但不能由 M1 擅自决定。

ADMIN 不因拥有 D 的全局管理能力就自动获得新增 M1 权限。即使显式获授 read-own，也只表示本人历史；运营查询是 B 的独立业务权限，另行确定。管理员个人预约能否跨院系也须明确，本稿建议先与普通预约遵守相同范围，不增加代约能力。

变更归属：D 维护权限目录、角色及授权；通过新的版本化迁移演进，不改已应用的 V1/V2。迁移需可从空库重放并由 Flyway 重跑安全；不在本轮执行迁移或批量改变真实账号角色。

### 3.2 预约开放范围

`departmentId` 目前是资源管理归属，不能同时推定“全校可约”或“只限本院系”。建议只在 ROOM 主数据新增：

```json
{
  "bookingScope": "DEPARTMENT"
}
```

另一取值为 `CAMPUS`；名字仅为本稿建议，正式字段由 D 评审确定。

| 建议值 | 普通预约者的范围规则 |
| --- | --- |
| DEPARTMENT | 有相应业务权限，且身份院系与教室 departmentId 相同 |
| CAMPUS | 有相应业务权限；不要求身份院系与管理院系相同 |

座位沿用所属教室范围，不各自维护第二份访问策略。管理归属保持原有含义与不可变约束。旧教室迁移建议先设 DEPARTMENT，避免未确认即向全校开放；D 可核实后通过版本校验的管理操作改为 CAMPUS。

接入建议：先按已验证身份检查业务权限，再依据 D 返回的教室 bookingScope 判定范围。院系来自 D 的身份/资源，不接受前端指定院系作为授权依据。对 CAMPUS 不向现有 authorization 强加教室 departmentId，否则会误拒绝合法的跨院系用户；对 DEPARTMENT 仍做本人院系比较，不能仅依赖 D 的 ADMIN 全局例外。

兼容建议：Resource 响应、创建/更新DTO、管理表单和类型定义共同演进；新字段在更新请求中省略时保留原值，不能被旧页面重置。旧创建请求若允许兼容，则缺省为 DEPARTMENT；其他资源类型不接受独立 bookingScope。未知/缺失范围在接入未完成时不能默认作 CAMPUS。

### 3.3 插座标记

建议保留现有 features 数组，在 SEAT 上统一使用精确标记 `POWER_OUTLET`，界面显示“有插座”。例如：

```json
{
  "type": "SEAT",
  "features": ["POWER_OUTLET"]
}
```

筛选“有插座”时只返回带此标记的座位。教室 features 里的“电源插座”不能推断每个座位都有插座；未标记表示没有已确认标记，不声称物理上一定没有插座。

相比新增布尔字段，此方案能沿用现有数组结构；代价是 D 仍需统一词汇、输入控件及历史数据。当前演示使用座位“电源”、教室“电源插座”，不能由 M1 字符串猜测后自动批量替换；D 维护者需核实要转换的座位。若 D 更倾向结构化布尔字段也可评审替代，本稿不同时维护两套含义不一致的属性。

## 4. 完整接入仍需明确的边界

这些问题在原文已有提醒或已从现有实现发现，不应被前三项字段建议掩盖：

- **主数据停用竞态。** 实时查询和 resourceVersion 不能提供 D/M1 跨服务原子性。建议讨论两种口径：以提交前最终校验时点为准，容许校验后发生停用的在途请求完成；或要求停用提交后绝不再产生新预约，后者需要额外的跨服务协调/屏障方案。前者实现较小，但必须明确说明其边界并由 A/D 确认，不能擅自宣称“停用立即阻止所有在途请求”。既有预约处置和范围收紧也要单独约定。
- **午夜开放表示。** 文档写跨夜拆分，但当前 LocalTime 的 end 不能表达24:00。建议 D 明确是否需要开放至午夜；若需要，可评审支持 end=24:00 的端点表示及相应DTO/客户端兼容方式。在此之前，M1不推断跨午夜完整覆盖；不能删去未完成项来宣称全场景完成。
- **调用失败与超时。** 建议连接1秒、读取2秒、一次业务调用预算3秒，均配置化、待联调调整；重试不得突破总预算。无效会话、权限拒绝、正常空结果和D不可用分别处理，不借旧缓存放行写入，日志不包含会话或服务密钥。
- **同源路由和CSRF。** 沿用D登录和Cookie；M1自己的HTTP写入口仍须CSRF验证。D源码使用CookieCsrfTokenRepository，但这不等于独立M1服务已经完成同样验证；需评审M1路径、Cookie/Header命名和前端取令牌流程，不能只转发一个头就声称已保护写入。
- **配置与通知。** 预约窗口/时长参数管理归属尚待确定；通知渠道也不能由本稿越过B后续设计。站内信接口可复用，课程提醒的最终验收方式另列。用户“一天”按滚动24小时的具体化建议也没有因本稿变成已确认规则。

## 5. 建议验收条件与工作归属

| 验收例子 | 预期 |
| --- | --- |
| 同一有效会话无创建权限，即使有spaces.write | 拒绝预约 |
| 有创建权限但前端提交他人userId | 不得为他人预约；身份只来自会话 |
| DEPARTMENT教室，本院系/外院系普通用户 | 前者在其他条件满足时允许，后者拒绝 |
| CAMPUS教室，外院系且有业务权限 | 在其他条件满足时允许 |
| 拥有read-own的管理员访问他人历史 | 不能凭该权限读取 |
| 教室标记有插座，目标座位没有标准标记 | 不列入“有插座”筛选结果 |
| 标记POWER_OUTLET但座位停用/时段不开放/有占用 | 仍排除 |
| 父级停用但座位version未变 | 仍通过新effectiveActive判断停用 |
| D鉴权超时、资源分页中途失败 | 明确服务不可用，不返回完整成功或当作空座位 |
| 新迁移空库执行及再次启动Flyway、旧页面更新资源 | 迁移可重放；重复安全；新增范围不被省略字段重置 |
