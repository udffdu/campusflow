## 本轮实现

- M1自有m1 schema，V1迁移包含reservations、reservation_requests、outbox_events。用Flyway管理迁移，不访问D表。
- ReservationStore独立READ COMMITTED事务中按用户和教室取得排序后的事务级advisory lock；取得锁后校验幂等、时间和有效个人预约冲突。
- 预约、幂等引用和待发业务事件同事务提交；锁等待超时/死锁/序列化失败报告STORAGE_UNAVAILABLE。
- 相同主体/键/意图重试返回同一预约的当前状态；不同意图拒绝。元数据resourceVersion变化不改变用户请求摘要。
- 仅提供内部Java创建和按用户查单条记录的方法。尚无HTTP、D鉴权、完整可用性计算、M2/M3接口、状态转换或事件投递器。

## 破坏实验

```sh
python3 scripts/check_m1_core_mutations.py --output-dir /tmp/campusflow-m1-mutations
```

在一次性源码副本中执行，三个实验均观察到指定行为断言失败，0测试执行错误；源码前后SHA-256相同。

1. 把半开区间改成包含相邻端点：核心组出现3个断言失败。
2. 删除窗口上限校验：核心组出现2个断言失败。
3. 删除数据库锁获取：专门的持锁等待用例失败，证明它检测了真实数据库锁的存在。

脚本选择相关测试组，要求出现预期断言失败，编译失败或未运行预期用例不算成功。正常源码的完整43测试已通过，不把故意失败的副本作为正式实现。

## 边界与待完成

- 内部调用方仍必须认证用户并从D核实座位/教室关系、权限、院系范围、开放时间和资源有效性。不能把Java参数当作可信HTTP载荷。
- 当前冲突检查只含个人预约，M2/M3写入及其查询尚未接入；不能声称跨模块占用链路已打通。
- 事务锁是所有写入方必须遵守的协议；数据库正区间/状态等约束并不是跨行重叠排他约束，不允许其他写入口绕过锁协议。
- 事件仅保存为PENDING，未发送给D，更未证明邮件/微信提醒已送达。
- 重放依然要求未来应用层校验当前身份。ResourceVersion不作为跨服务原子锁，管理员停用竞态仍待D契约评审。
- 当前create自带REQUIRES_NEW事务，不能假定会随调用方外层事务回滚；其他模块不得把跨服务调用当作本地同一事务。
- 尚未运行远程CI、推送或部署；本批在用户报告复验成功后分步本地提交，其他成员评审未完成。本轮不修改D/M2/M3契约及schema。
